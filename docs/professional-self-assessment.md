Completing the Computer Science program and developing my ePortfolio has changed the way I think about software development as much as it has expanded my technical abilities. Earlier in the program, I was often primarily concerned with whether I could get a program to work and satisfy its requirements. As I progressed through courses involving software design, algorithms, databases, security, testing, systems development, and project planning, I began to understand how much more goes into developing good software. Maintainability, reliability, security, documentation, and communication have become just as important to me as writing the code itself. Revisiting earlier projects for my ePortfolio made this growth especially apparent because I could look at working applications I had previously completed and recognize how differently I would approach their design today. This process has helped me better understand my strengths and reinforced my goal of pursuing embedded engineering or another field where software interacts closely with physical hardware and real-world systems.

One area where I have grown considerably is in understanding collaboration and communication within software development. Throughout the program, I learned that collaboration does not only mean multiple programmers writing code together. Developers also need to understand stakeholder requirements, communicate technical decisions, and leave their work in a state where other people can understand and continue it. Courses involving the software development life cycle and systems analysis helped me consider software from the perspective of clients and users instead of only the programmer. I also developed a much greater appreciation for documentation. Early in the program, documentation often felt secondary to getting the code working, but I now understand that good documentation is itself a form of collaboration. Requirements, diagrams, comments, README files, and technical explanations allow other developers to understand both how a system works and why certain decisions were made. Developing my ePortfolio strengthened this skill further because I had to communicate my work through code reviews, enhancement narratives, project documentation, and the portfolio itself for audiences who were not involved in the original development.

My understanding of software engineering has also changed substantially. Object-oriented programming, modular design, separation of concerns, testing, error handling, and configuration management have all influenced the way I approach a project. Instead of only asking whether a program works, I now consider whether its components have clearly defined responsibilities, whether changes can be made without affecting unrelated functionality, and whether another developer could reasonably understand and maintain the application. Automated testing has become particularly important because it provides a repeatable way to verify that changes to one part of a system have not unintentionally affected another. The capstone reinforced these lessons by requiring me to return to existing applications and improve them instead of starting over, which better reflects professional development where programmers often need to understand, maintain, and extend existing systems.

Data structures and algorithms gave me another way of looking at software design by demonstrating that there is rarely one structure or algorithm that is best for every problem. Concepts involving searching, sorting, hashing, ordered structures, and algorithmic complexity helped me understand how the organization of data affects the efficiency of an application. Rather than choosing a data structure simply because it works, I have learned to consider the operations a system performs most frequently and the trade-offs involving performance, memory, maintainability, and scalability. This type of algorithmic thinking has also influenced how I approach software architecture because evaluating possible solutions and understanding their trade-offs is an important part of designing larger systems.

My database coursework expanded that thinking into how applications store, retrieve, and use information. Through database development, I gained experience with CRUD operations, MongoDB, query design, indexing, filtering, aggregation, and reporting. More importantly, I learned that simply storing data does not make it useful. Information needs to be validated, retrieved efficiently, and presented in a way that supports the people using the system. The capstone especially changed how I think about reporting because I learned how complex a useful reporting dashboard can become when searching, filtering, validation, visualization, and different user needs all have to work together. This gave me a greater appreciation for the relationship between database design, application performance, and the decisions that software is ultimately intended to support.

Security has similarly become something I view as part of the design process rather than a feature that can be added after an application is finished. Coursework involving secure coding taught me to consider not only how users are expected to interact with a system, but also what can happen when invalid, unexpected, or malicious input is provided. Input validation, credential management, data privacy, error handling, and limiting unnecessary exposure of information are now considerations I try to incorporate into an application from the beginning. Creating a public ePortfolio provided a practical example because publishing source code required me to consider whether projects contained database credentials, passwords, personal information, or other information that should not be publicly exposed. Applying these ideas during my database enhancement by removing hardcoded credentials and strengthening validation helped reinforce the importance of anticipating security concerns instead of responding to them only after a problem occurs.

Together, these experiences have helped shape both my professional values and the type of career I want to pursue. I have realized that I am most interested in computer science when software is part of a larger physical system rather than existing entirely on a screen. Embedded engineering appeals to me because it combines programming with hardware, communication, sensors, electronics, and systems-level problem solving. Areas such as audio technology, medical devices, and industrial equipment are especially interesting to me because they provide opportunities to develop software with a tangible real-world purpose. At the same time, the program has shown me that becoming a capable computer scientist requires more than proficiency in a particular programming language. Some of my most important growth has come from learning how to break larger problems into manageable components, evaluate different approaches, test my assumptions, document my work, communicate with others, and continue learning when I encounter unfamiliar technology.

The three artifacts included in my ePortfolio demonstrate different but complementary areas of that growth. The **LED/LCD State Simulator** from CS 350 represents Software Engineering and Design and demonstrates modular architecture, embedded programming, hardware communication, concurrency, and maintainability. The **Appointment Service Scheduler** from CS 320 represents Algorithms and Data Structures and demonstrates how appropriate data structures, scheduling logic, validation, and a suite of 37 automated tests can strengthen an existing application. The **Grazioso Salvare Animal Shelter Dashboard** from CS 340 represents Databases and demonstrates MongoDB data management, searching, indexing, geospatial functionality, reporting, secure configuration, automated testing, and modular application design.

Although these artifacts focus on different categories, they also demonstrate how closely those areas depend on one another in real software development. A complete system needs maintainable architecture, appropriate algorithms and data structures, effective data management, testing, security, and clear communication. Enhancing these projects allowed me to demonstrate each area individually while also seeing how they contribute to a larger development process. Together with my code review, documentation, and enhancement narratives, the artifacts that follow demonstrate not only what I can build, but how my ability to design, evaluate, test, document, and improve software has developed throughout the Computer Science program.
