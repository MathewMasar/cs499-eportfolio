# Professional Self-Assessment

Completing the Computer Science program and developing my ePortfolio has changed the way I think about software development as much as it has expanded my technical abilities. Earlier in the program, I was often primarily concerned with whether I could get a program to work and satisfy its requirements. As I progressed, I began to understand that good software requires much more than functional code. Maintainability, reliability, security, documentation, and communication have become important parts of how I evaluate a solution. Revisiting earlier projects for my ePortfolio made this growth especially apparent because I could look at working applications I had previously completed and recognize how differently I would approach their design today.

One area where I have grown considerably is collaboration and communication. I learned that collaboration does not only mean multiple programmers writing code together. Developers need to understand stakeholder requirements, communicate technical decisions, and leave their work in a state that other people can understand and continue. I also developed a much greater appreciation for documentation. Requirements, diagrams, comments, README files, and technical explanations communicate both how a system works and why certain decisions were made. Creating my ePortfolio reinforced this by requiring me to explain existing code, planned improvements, implementation decisions, and completed enhancements to an audience that was not involved in the original development.

My understanding of software engineering has changed in a similar way. Instead of only asking whether a program works, I now consider whether its components have clear responsibilities, whether changes can be made without unnecessarily affecting other functionality, and whether another developer could reasonably understand and maintain the application. Testing has also become an important part of that process because it provides a repeatable way to determine whether changes introduce unexpected behavior. The capstone reinforced these ideas by requiring me to understand, maintain, and improve existing applications rather than simply replace them.

Algorithms and data structures taught me that a working solution is not automatically the most appropriate solution. Different structures are suited to different operations, and selecting between them requires considering efficiency, scalability, memory, maintainability, and the behavior the application needs to support. More broadly, this taught me to evaluate alternatives and make intentional design decisions rather than selecting an approach simply because it produces the expected result.

My database coursework expanded that thinking into how applications store and use information. I learned that storing data is only one part of building a useful system. Data must also be validated, retrieved efficiently, organized appropriately, and presented in a way that supports the people using the application. Developing the database artifact in my capstone gave me a greater appreciation for how database design, application architecture, and reporting work together to turn stored records into useful information.

Security has also become something I view as part of the design process rather than a feature added after an application is finished. Input validation, credential management, data privacy, error handling, and limiting unnecessary exposure of information are considerations that should be addressed throughout development. Publishing source code through a public ePortfolio made this especially practical because I had to consider what information should and should not be exposed. This reinforced the importance of anticipating security concerns during development instead of responding to them only after a problem occurs.

Together, these experiences have helped shape both my professional values and the type of career I want to pursue. I am particularly interested in computer science when software interacts with physical hardware and real-world systems. Embedded engineering appeals to me because it combines programming with hardware, communication, sensors, electronics, and systems-level problem solving. Areas such as audio technology, medical devices, and industrial equipment are especially interesting because they provide opportunities to develop software with a tangible purpose. At the same time, the program has shown me that becoming a capable computer scientist requires more than proficiency in a particular programming language. Breaking larger problems into manageable components, evaluating alternatives, testing assumptions, documenting decisions, communicating clearly, and continuing to learn are skills that apply regardless of the technology being used.

The three artifacts in my ePortfolio demonstrate complementary areas of this development. The **LED/LCD State Simulator** focuses on software engineering and embedded-system design, the **Appointment Service Scheduler** demonstrates algorithms and data structures, and the **Grazioso Salvare Animal Shelter Dashboard** focuses on database-driven application development. Each enhancement began with working software and asked how that software could be improved intentionally rather than simply made more complex.

Although the artifacts represent different areas of computer science, they demonstrate a common development process. Software architecture, algorithms, data management, testing, security, and communication do not exist independently in larger systems. The enhancements required me to consider how these areas work together while solving practical limitations in the original applications. Documentation was an important part of that process because code reviews, README files, enhancement narratives, comments, and project organization make both the implementation and the reasoning behind it clearer to others.

Together, these artifacts demonstrate not only what I can build, but how my approach to software development has changed. My goal is to write code intentionally, choose solutions for defensible reasons, test and evaluate those decisions, and leave software in a state that another developer can understand and continue. That growth in how I design, evaluate, document, and improve software is the most important result of my Computer Science program.
